## Approach

Merge `AccomplishmentLootListener`'s allowlist logic into `LootAlertListener`, which becomes the single subscriber for all three loot sources (`NpcLootReceived`, `PlayerLootReceived`, and `LootReceived` filtered to `EVENT`/`PICKPOCKET`), independently checking each item against the value-threshold rule and the (now 7-item) mega-rare allowlist. Also close a chat-message-spoofing gap in `PetDropListener` and `OneTimeRewardListener` by adding a `ChatMessageType.GAMEMESSAGE` filter to both, verified against a real reference plugin (`discord-notifications`) that does the same, plus a third confirmed pet-message variant from that same plugin.

## Layers affected

- Alerts (`LootAlertListener.java`, deletion of `AccomplishmentLootListener.java`, `PetDropListener.java`, `OneTimeRewardListener.java`)
- Plugin Core (`CatastrophicEventsPlugin.java` registration)

## Conventions to follow

- Allman brace style, tab indentation

- Existing per-feature gating (`config.xEnabled()`) and `ApiCallback` async pattern

## Steps

### Step 1 — Subscribe to LootReceived
`LootAlertListener.java`: add `@Subscribe onLootReceived(LootReceived event)`, filtered to `event.getType() == LootRecordType.EVENT || event.getType() == LootRecordType.PICKPOCKET`, calling the existing `handleLoot(event.getItems(), event.getName())`. Imports: `net.runelite.client.plugins.loottracker.LootReceived`, `net.runelite.http.api.loottracker.LootRecordType`.

### Step 2 — Absorb the mega-rare allowlist
`LootAlertListener.java`: add a `TRACKED_ACCOMPLISHMENT_ITEM_IDS` `Set<Integer>` (`ItemID.TWISTED_BOW`, `SCYTHE_OF_VITUR`, `TUMEKENS_SHADOW`, `ANCIENT_BLOOD_ORNAMENT_KIT`, `MOKHAIOTL_CLOTH`, `EYE_OF_AYAK_UNCHARGED`, `AVERNIC_TREADS`). Within `handleLoot`, add an independent check: if `item.getId()` is in that set, fire an `AlertKind.ACCOMPLISHMENT` alert (screenshot + title=`composition.getName()` + summary=`"received {name} from {source}"`) gated on `config.accomplishmentSharingEnabled()`, alongside (not replacing) the existing value-threshold `AlertKind.LOOT` check. Mirror `AccomplishmentLootListener`'s exact `sendAlert(...)` call shape (the title-carrying overload).

### Step 3 — Delete the old listener
Delete `alerts/AccomplishmentLootListener.java`.

### Step 4 — Update plugin registration
`CatastrophicEventsPlugin.java`: remove the `accomplishmentLootListener` field/`@Inject`, and its `eventBus.register(...)`/`unregister(...)` calls in `startUp()`/`shutDown()`.

### Step 5 — Manual QA (loot consolidation)
`./gradlew compileJava` to confirm it compiles clean, including that `LootReceived`/`LootRecordType` resolve without a new `build.gradle` dependency (already transitively available via `net.runelite:client`).

### Step 6 — Fix PetDropListener spoofing
`PetDropListener.java`: add `if (event.getType() != ChatMessageType.GAMEMESSAGE) { return; }` at the top of `onChatMessage`, before the text match (import `net.runelite.api.ChatMessageType`). Add the third pattern alternative `"funny feeling like you would have been followed"` to the `PET_OBTAINED` `Pattern`.

### Step 7 — Fix OneTimeRewardListener spoofing
`OneTimeRewardListener.java`: add the same `if (event.getType() != ChatMessageType.GAMEMESSAGE) { return; }` filter at the top of `onChatMessage`, before the text match (same import).

### Step 8 — Resolve WRN-006
`concerns.json`: mark WRN-006 resolved — both listeners now filter by `ChatMessageType.GAMEMESSAGE`, closing the chat-spoofing exploit vector confirmed via a real Discord incident. Note in the resolution that `OneTimeRewardListener`'s exact wording is still best-effort/unconfirmed against a live client, but the spoofing risk itself is closed.
